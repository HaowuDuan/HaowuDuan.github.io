<p>The two ranks in a TP pair hold complementary shards of the same
layer and must exchange partial results. A rank from another DP or PP
pair is working on different data or a different pipeline stage.
Including that rank in the TP collective would mix unrelated
computations.</p>
<p>OLMo constructs the world mesh once and extracts the submesh needed
by each parallel method. The layer implementations then use the
corresponding process groups for their collective operations:</p>
<pre class="code-block"><code class="language-python">world_mesh = build_world_mesh(&#10;    dp=dp_config,&#10;    tp=tp_config,&#10;    cp=cp_config,&#10;    pp=pp_config,&#10;    ep=ep_config,&#10;)&#10;&#10;tp_mesh = get_tp_mesh(world_mesh)&#10;cp_mesh = get_cp_mesh(world_mesh)&#10;pp_mesh = get_pp_mesh(world_mesh)&#10;ep_mesh = get_ep_mesh(world_mesh)</code></pre>
<p>The implementation checks that every enabled degree divides the world
size. It also requires a data-parallel configuration whenever TP, PP,
CP, or EP is enabled <span class="citation">[<a href="#ref-olmo-world-mesh">1</a>]</span>.</p>

<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6833em;"></span><span class="mord mathnormal" style="margin-right:0.0278em;">D</span></span></span></span>

query, key, and value vectors to compute attention across sequence

the output projection.</p>
<p>OLMo applies the MLP’s TP pattern to these projections. The query,
key, and value projections are column-wise, so each TP rank computes a
subset of the heads. The output projection is row-wise and combines the
results from those subsets <span class="citation">[<a href="#ref-olmo-attention">4</a>]</span>.</p>
<p>At transformer-block boundaries, OLMo keeps activations sharded along
the sequence axis of the TP group. Layer normalization and dropout then
run on the local sequence slices. OLMo calls this <em>sequence
parallelism</em>; it is a companion layout used inside TP and is
distinct from the context-parallel mode described next <span class="citation">[<a href="#ref-olmo-transformer-block">5</a>]</span>.</p>
<h2 id="context-parallelism-splits-a-long-sequence">Context parallelism
splits a long sequence</h2>
<p>Suppose two CP ranks process one sequence of eight tokens. In the
simplest split, rank 0 holds positions
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6444em;"></span><span class="mord">0</span></span></span></span>
through
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6444em;"></span><span class="mord">3</span></span></span></span>,
and rank 1 holds positions
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6444em;"></span><span class="mord">4</span></span></span></span>
through
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6444em;"></span><span class="mord">7</span></span></span></span>.
CP divides the sequence activations, not the parameter tensors; FSDP may
separately shard those parameters. The difficulty is attention: a query
in one slice may need keys and values from the other slice.</p>
<p>OLMo supports two ways to exchange the missing attention
information.</p>
<h3 id="ring-attention">Ring attention</h3>
<p>Each rank keeps its local queries. Key and value blocks circulate
around the CP group. A rank updates its attention result when each
key/value block arrives. After one trip around the ring, every local
query has attended to all allowed positions, but no rank had to store
the complete sequence’s keys and values at once.</p>
<h3 id="ulysses-attention">Ulysses attention</h3>
<p>Let the CP group contain
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6833em;"></span><span class="mord mathnormal" style="margin-right:0.0715em;">C</span></span></span></span>
ranks, and assume that
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6833em;"></span><span class="mord mathnormal">A</span></span></span></span>
is divisible by
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6833em;"></span><span class="mord mathnormal" style="margin-right:0.0715em;">C</span></span></span></span>.
Initially, each rank holds all
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6833em;"></span><span class="mord mathnormal">A</span></span></span></span>
heads for only its own
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:1em;vertical-align:-0.25em;"></span><span class="mord mathnormal" style="margin-right:0.0576em;">S</span><span class="mord">/</span><span class="mord mathnormal" style="margin-right:0.0715em;">C</span></span></span></span>
sequence positions:</p>
<p><span class="equation-block" data-equation-numbers="14"><span class="katex-display"><span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:1.2em;vertical-align:-0.35em;"></span><span class="mord"><span class="mtable"><span class="col-align-r"><span class="vlist-t vlist-t2"><span class="vlist-r"><span class="vlist" style="height:0.85em;"><span style="top:-3.01em;"><span class="pstrut" style="height:3em;"></span><span class="mord"><span class="mopen">[</span><span class="mord mathnormal" style="margin-right:0.0502em;">B</span><span class="mpunct">,</span><span class="mspace" style="margin-right:0.1667em;"></span><span class="mord mathnormal" style="margin-right:0.0576em;">S</span><span class="mord">/</span><span class="mord mathnormal" style="margin-right:0.0715em;">C</span><span class="mpunct">,</span><span class="mspace" style="margin-right:0.1667em;"></span><span class="mord mathnormal">A</span><span class="mpunct">,</span><span class="mspace" style="margin-right:0.1667em;"></span><span class="mord mathnormal" style="margin-right:0.0278em;">D</span><span class="mclose">]</span><span class="mpunct">,</span></span></span></span><span class="vlist-s">​</span></span><span class="vlist-r"><span class="vlist" style="height:0.35em;"><span></span></span></span></span></span></span></span></span></span></span></span><span class="equation-number" aria-hidden="true">(14)</span></span></p>
<p>This layout cannot run ordinary attention locally: one head needs
keys and values from all
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6833em;"></span><span class="mord mathnormal" style="margin-right:0.0576em;">S</span></span></span></span>
positions, but each rank has only
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:1em;vertical-align:-0.25em;"></span><span class="mord mathnormal" style="margin-right:0.0576em;">S</span><span class="mord">/</span><span class="mord mathnormal" style="margin-right:0.0715em;">C</span></span></span></span>
positions. Ulysses exchanges sequence coverage for head coverage. Every
rank divides its
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6833em;"></span><span class="mord mathnormal">A</span></span></span></span>
heads into
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6833em;"></span><span class="mord mathnormal" style="margin-right:0.0715em;">C</span></span></span></span>
groups and sends one head group to each CP rank. A receiving rank gets
the same head group from all
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6833em;"></span><span class="mord mathnormal" style="margin-right:0.0715em;">C</span></span></span></span>
sequence slices and concatenates those slices along the sequence axis.
Its new layout is</p>
<p><span class="equation-block" data-equation-numbers="15"><span class="katex-display"><span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:1.2em;vertical-align:-0.35em;"></span><span class="mord"><span class="mtable"><span class="col-align-r"><span class="vlist-t vlist-t2"><span class="vlist-r"><span class="vlist" style="height:0.85em;"><span style="top:-3.01em;"><span class="pstrut" style="height:3em;"></span><span class="mord"><span class="mopen">[</span><span class="mord mathnormal" style="margin-right:0.0502em;">B</span><span class="mpunct">,</span><span class="mspace" style="margin-right:0.1667em;"></span><span class="mord mathnormal" style="margin-right:0.0576em;">S</span><span class="mpunct">,</span><span class="mspace" style="margin-right:0.1667em;"></span><span class="mord mathnormal">A</span><span class="mord">/</span><span class="mord mathnormal" style="margin-right:0.0715em;">C</span><span class="mpunct">,</span><span class="mspace" style="margin-right:0.1667em;"></span><span class="mord mathnormal" style="margin-right:0.0278em;">D</span><span class="mclose">]</span><span class="mpunct">,</span></span></span></span><span class="vlist-s">​</span></span><span class="vlist-r"><span class="vlist" style="height:0.35em;"><span></span></span></span></span></span></span></span></span></span></span></span><span class="equation-number" aria-hidden="true">(15)</span></span></p>
<p>The rank now has the complete sequence for
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:1em;vertical-align:-0.25em;"></span><span class="mord mathnormal">A</span><span class="mord">/</span><span class="mord mathnormal" style="margin-right:0.0715em;">C</span></span></span></span>
heads, so it computes ordinary full-sequence attention for those heads.
The reverse all-to-all then does the opposite: each rank divides its
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6833em;"></span><span class="mord mathnormal" style="margin-right:0.0576em;">S</span></span></span></span>
output positions into
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6833em;"></span><span class="mord mathnormal" style="margin-right:0.0715em;">C</span></span></span></span>
chunks and sends one chunk back to each original sequence owner. Each
owner receives all
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6833em;"></span><span class="mord mathnormal">A</span></span></span></span>
head groups for its own
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:1em;vertical-align:-0.25em;"></span><span class="mord mathnormal" style="margin-right:0.0576em;">S</span><span class="mord">/</span><span class="mord mathnormal" style="margin-right:0.0715em;">C</span></span></span></span>
positions, restoring
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:1em;vertical-align:-0.25em;"></span><span class="mopen">[</span><span class="mord mathnormal" style="margin-right:0.0502em;">B</span><span class="mpunct">,</span><span class="mspace" style="margin-right:0.1667em;"></span><span class="mord mathnormal" style="margin-right:0.0576em;">S</span><span class="mord">/</span><span class="mord mathnormal" style="margin-right:0.0715em;">C</span><span class="mpunct">,</span><span class="mspace" style="margin-right:0.1667em;"></span><span class="mord mathnormal">A</span><span class="mpunct">,</span><span class="mspace" style="margin-right:0.1667em;"></span><span class="mord mathnormal" style="margin-right:0.0278em;">D</span><span class="mclose">]</span></span></span></span>.
OLMo implements these two layout transformations explicitly <span class="citation">[<a href="#ref-olmo-context-parallel">6</a>]</span>.</p>
<p>The model shards input IDs, labels, and positional-encoding buffers
with the same CP assignment before the forward pass. The configuration
selects either the ring method or the Ulysses method <span class="citation">[<a href="#ref-olmo-transformer-model">7</a>, <a href="#ref-olmo-train-config">8</a>]</span>.</p>
<p>This also explains the connection to the data loader. Ranks in one CP
group receive the same model input. CP divides that input during model
computation; it does not ask the data loader for different
examples <span class="citation">[<a href="#ref-olmo-world-mesh">1</a>]</span>.</p>
<h2 id="pipeline-parallelism-splits-the-block-list">Pipeline parallelism
splits the block list</h2>
<p>Consider an eight-block transformer and two pipeline stages:</p>

class="vlist-r"><span class="vlist" style="height:1.6em;"><span style="top:-3.76em;"><span class="pstrut" style="height:3em;"></span><span class="mord"><span class="mord text"><span class="mrel">:</span></span></span></span><span class="vlist-s">​</span></span><span class="vlist-r"><span class="vlist" style="height:1.1em;"><span></span></span></span></span></span><span class="col-align-l"><span class="vlist-t vlist-t2"><span class="vlist-r"><span class="vlist" style="height:1.6em;"><span style="top:-3.76em;"><span class="pstrut" style="height:3em;"></span><span class="mspace" style="margin-right:0.2778em;"></span><span class="mspace" style="margin-right:0.1667em;"></span><span class="mord text"><span class="mord">blocks </span></span><span class="mord">0</span><span class="mord text"><span class="mord">–</span></span><span class="mord">3</span><span class="mpunct">,</span></span></span><span style="top:-2.26em;"><span class="pstrut" style="height:3em;"></span><span class="mord"><span class="mord"></span><span class="mspace" style="margin-right:1em;"></span><span class="mord text"><span class="mord">blocks </span></span><span class="mord">4</span><span class="mord text"><span class="mord">–</span></span><span class="mord">7</span><span class="mpunct">,</span><span class="mspace" style="margin-right:0.2778em;"></span><span class="mspace" style="margin-right:0.1667em;"></span><span class="mord text"><span class="mord">LM head</span></span><span class="mord">.</span></span></span></span><span class="vlist-s">​</span></span><span class="vlist-r"><span class="vlist" style="height:1.1em;"><span></span></span></span></span></span></span></span></span></span></span></span><span class="equation-number" aria-hidden="true">(16)</span></span></p>
<p>Equation <a class="equation-reference" href="#eq:pipeline-stage-assignment">(16)</a>
assigns model components to stages; it is not a computation. OLMo turns
each assignment into a smaller model by copying the transformer and
deleting the unassigned components. The first stage keeps the embedding
because it receives token IDs, the last keeps the language-model head
because it produces logits, and each stage keeps only its assigned block
interval.</p>
<p>PyTorch’s <code>PipelineStage</code> wraps each smaller model with
its stage index, device, and pipeline process group. The pipeline
schedule then sends hidden states from one stage to the next during
forward and sends their gradients in the reverse direction during
backward <span class="citation">[<a href="#ref-olmo-pipeline-config">9</a>]</span>.</p>
<p>The batch is divided into microbatches so that different stages can
work on different microbatches at the same time. Each stage stores and
updates only the parameters of its smaller model.</p>
<pre class="code-block"><code class="language-python">&#35; Simplified construction of one pipeline stage.&#10;model_part = copy.deepcopy(model)&#10;&#10;if not is_first_stage:&#10;    model_part.embeddings = None&#10;if not is_last_stage:&#10;    model_part.lm_head = None&#10;&#10;delete_blocks_outside_this_stage(model_part)&#10;stage = PipelineStage(model_part, stage_id, num_stages, device)</code></pre>
<p>OLMo constructs the configured schedule with the selected number of
microbatches. It does not support tied input and output embeddings
across multiple stages because those weights would be placed in
different stage-local models <span class="citation">[<a href="#ref-olmo-pipeline-train">10</a>, <a href="#ref-olmo-pipeline-config">9</a>]</span>.</p>
<h2 id="expert-parallelism-splits-the-experts">Expert parallelism splits
the experts</h2>
<p>In a mixture-of-experts layer, a router selects a small number of
experts for each token. Suppose there are four experts and two EP
ranks:</p>
<p><span class="equation-block" data-equation-numbers="17"><span class="katex-display"><span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:1.2em;vertical-align:-0.35em;"></span><span class="mord"><span class="mtable"><span class="col-align-r"><span class="vlist-t vlist-t2"><span class="vlist-r"><span class="vlist" style="height:0.85em;"><span style="top:-3.01em;"><span class="pstrut" style="height:3em;"></span><span class="mord"><span class="mord text"><span class="mord">rank 0 owns experts </span></span><span class="mopen">{</span><span class="mord">0</span><span class="mpunct">,</span><span class="mspace" style="margin-right:0.1667em;"></span><span class="mord">1</span><span class="mclose">}</span><span class="mpunct">,</span><span class="mspace" style="margin-right:2em;"></span><span class="mspace" style="margin-right:0.1667em;"></span><span class="mord text"><span class="mord">rank 1 owns experts </span></span><span class="mopen">{</span><span class="mord">2</span><span class="mpunct">,</span><span class="mspace" style="margin-right:0.1667em;"></span><span class="mord">3</span><span class="mclose">}</span><span class="mord">.</span></span></span></span><span class="vlist-s">​</span></span><span class="vlist-r"><span class="vlist" style="height:0.35em;"><span></span></span></span></span></span></span></span></span></span></span></span><span class="equation-number" aria-hidden="true">(17)</span></span></p>
<p>A token initially resides on the rank that is processing its input
sequence. Its selected expert may reside on the other rank. The forward
pass therefore has five steps:</p>
<div class="center">
<p>route tokens
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.522em;vertical-align:-0.011em;"></span><span class="mrel">⟶</span></span></span></span>
group by destination rank
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.522em;vertical-align:-0.011em;"></span><span class="mrel">⟶</span></span></span></span>
all-to-all
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.522em;vertical-align:-0.011em;"></span><span class="mrel">⟶</span></span></span></span>
local expert computation
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.522em;vertical-align:-0.011em;"></span><span class="mrel">⟶</span></span></span></span>
reverse all-to-all.</p>
</div>
<p>The returned outputs are restored to their original token order and
combined with the router weights. OLMo implements this order as
<code>permute_and_all_to_all</code>, local expert computation,
<code>reverse_all_to_all</code>, and <code>unpermute</code> <span class="citation">[<a href="#ref-olmo-parallel-mlp">12</a>]</span>.</p>
<p>The expert weight tensors are sharded along their expert dimension,
so each rank permanently stores only its local experts <span class="citation">[<a href="#ref-olmo-expert-mlp">11</a>]</span>. At the pinned
OLMo revision used here, EP requires HSDP, and TP and EP cannot be
enabled together <span class="citation">[<a href="#ref-olmo-world-mesh">1</a>, <a href="#ref-olmo-parallelize-model">2</a>]</span>.</p>
<h2 id="how-olmo-constructs-the-parallel-model">How OLMo constructs the
parallel model</h2>
<p>The process mesh defines rank groups. The model-parallel methods then
replace ordinary local modules with distributed layouts and
communication. OLMo performs these transformations before constructing
the optimizer.</p>
<figure id="fig:olmo-parallel-construction">
<img src="/notes/model-parallelism/olmo-parallel-construction.svg" alt="The order in which OLMo builds its process mesh, applies pipeline, context, tensor or expert, and data parallelism, initializes local parameters, and constructs the optimizer." />
<figcaption>OLMo transforms the model before training begins. Each
optimizer sees only the parameters represented on its rank after all
parallel transformations.</figcaption>
</figure>
<p>The essential control flow is visible in the original implementation
<span class="citation">[<a href="#ref-olmo-parallelize-model">2</a>, <a href="#ref-olmo-pipeline-train">10</a>]</span>:</p>
<pre class="code-block"><code class="language-python">world_mesh = build_world_mesh(dp=dp, tp=tp, cp=cp, pp=pp, ep=ep)&#10;&#10;&#35; Pipeline training performs this split first.&#10;stages, model_parts = pp.split_model(model, pp_mesh=pp_mesh)&#10;&#10;&#35; The shared transformation applies CP, TP or EP, then DP.&#10;model_parts = parallelize_model(&#10;    model_parts,&#10;    world_mesh=world_mesh,&#10;    cp_config=cp,&#10;    tp_config=tp,&#10;    ep_config=ep,&#10;    dp_config=dp,&#10;)&#10;&#10;&#35; Each stage builds an optimizer for the parameters it now owns.&#10;optimizers = [optim.build(part) for part in model_parts]</code></pre>
<p>Without pipeline parallelism, the training loop calls the wrapped
model in the usual way, and its distributed modules perform the required
collectives. With pipeline parallelism, the training loop instead calls
the configured pipeline schedule; that schedule invokes each local stage
and performs the point-to-point transfers between stages.</p>
