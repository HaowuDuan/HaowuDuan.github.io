<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.522em;vertical-align:-0.011em;"></span><span class="mrel">⟶</span></span></span></span>

<p>Scikit-learn can create the split, <code>torch.from_numpy</code> can

<p>In PyTorch, the remembered tensor container is
<code>TensorDataset</code>, not <code>TensorLoader</code>. A standard
pipeline is:</p>
<pre class="code-block"><code class="language-python">from sklearn.model_selection import train_test_split&#10;import torch&#10;from torch.utils.data import TensorDataset, DataLoader&#10;&#10;&#35; Split NumPy arrays into training and validation sets.&#10;X_train, X_val, y_train, y_val = train_test_split(&#10;    X, y, test_size=0.1, random_state=42&#10;)&#10;&#10;&#35; TensorDataset stores corresponding input and target tensors.&#10;train_dataset = TensorDataset(&#10;    torch.from_numpy(X_train), torch.from_numpy(y_train)&#10;)&#10;val_dataset = TensorDataset(&#10;    torch.from_numpy(X_val), torch.from_numpy(y_val)&#10;)&#10;&#10;&#35; DataLoader chooses examples and combines them into minibatches.&#10;train_loader = DataLoader(train_dataset, batch_size=64, shuffle=True)&#10;val_loader = DataLoader(val_dataset, batch_size=64, shuffle=False)&#10;&#10;for x_batch, y_batch in train_loader:&#10;    prediction = model(x_batch)&#10;    loss = loss_fn(prediction, y_batch)</code></pre>

long token stream rather than a collection of stored input–label
pairs:</p>

tokenize
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.522em;vertical-align:-0.011em;"></span><span class="mrel">⟶</span></span></span></span>
train/validation token files
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.522em;vertical-align:-0.011em;"></span><span class="mrel">⟶</span></span></span></span>
sample token windows
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.522em;vertical-align:-0.011em;"></span><span class="mrel">⟶</span></span></span></span>

<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:1em;vertical-align:-0.25em;"></span><span class="mopen">(</span><span class="mord mathnormal">x</span><span class="mpunct">,</span><span class="mspace" style="margin-right:0.1667em;"></span><span class="mord mathnormal" style="margin-right:0.0359em;">y</span><span class="mclose">)</span></span></span></span>
batches.</p>
</div>
<p>NanoGPT implements the last two steps directly with
<code>get_batch()</code>. The training and validation split already
exists as <code>train.bin</code> and <code>val.bin</code>. The function
selects one file, samples windows, constructs the shifted inputs and
targets, and transfers them to the device:</p>
<pre class="code-block"><code class="language-python">def get_batch(split):&#10;    filename = &quot;train.bin&quot; if split == &quot;train&quot; else &quot;val.bin&quot;&#10;    data = np.memmap(filename, dtype=np.uint16, mode=&quot;r&quot;)&#10;    ix = torch.randint(len(data) - block_size, (batch_size,))&#10;    x = torch.stack([&#10;        torch.from_numpy(data[i:i + block_size].astype(np.int64))&#10;        for i in ix&#10;    ])&#10;    y = torch.stack([&#10;        torch.from_numpy(data[i + 1:i + 1 + block_size].astype(np.int64))&#10;        for i in ix&#10;    ])&#10;    return x.to(device), y.to(device)</code></pre>
<p>The tensor <code>ix</code> contains <code>batch_size</code> random
starting positions for the sampled token windows.</p>
<h2 id="distributed-data-parallel-ddp">Distributed Data Parallel
(DDP)</h2>
<p>Data parallelism divides one training batch among several GPUs.
Distributed Data Parallel (DDP) keeps one model replica on each GPU and
averages the gradients computed by those replicas <span class="citation">[<a href="#ref-li2020pytorchdistributed">1</a>]</span>.</p>

<p>Every rank owns an optimizer and calls <code>optimizer.step()</code>
using the same averaged gradient (g). Because the parameters and
optimizer states started equal, these separate updates produce equal
model replicas. DDP does not update one rank and then copy that model to
the others. DDP synchronizes gradients; it does not choose or divide the
data. The data loader must give each rank its local batch.</p>

<figcaption>Each rank computes a local gradient. DDP returns the same
averaged gradient to both ranks, and each rank updates its own
replica.</figcaption>
</figure>
<div class="minipage">
<p>The core PyTorch implementation uses DDP together with a distributed
sampler <span class="citation">[<a href="#ref-pytorch-ddp">2</a>, <a href="#ref-pytorch-distributed-sampler">3</a>]</span>:</p>
<pre class="code-block"><code class="language-python">import os&#10;import torch&#10;import torch.distributed as dist&#10;from torch.nn.parallel import DistributedDataParallel as DDP&#10;from torch.utils.data import DataLoader, DistributedSampler&#10;&#10;&#35; Join the processes started by torchrun. NCCL handles GPU collectives.&#10;dist.init_process_group(backend=&quot;nccl&quot;)&#10;&#10;&#35; torchrun assigns this process one GPU index on the current machine.&#10;local_rank = int(os.environ[&quot;LOCAL_RANK&quot;])&#10;&#10;&#35; Make that GPU the default CUDA device for this process.&#10;torch.cuda.set_device(local_rank)&#10;&#10;&#35; Give every rank the same number of examples. If the dataset size is not&#10;&#35; divisible by the number of ranks, drop the tail instead of padding the&#10;&#35; index list with duplicate examples.&#10;sampler = DistributedSampler(dataset, shuffle=True, drop_last=True)&#10;loader = DataLoader(dataset, batch_size=local_batch_size,&#10;                    sampler=sampler)&#10;&#10;model = Model().to(local_rank)&#10;model = DDP(model, device_ids=[local_rank])&#10;optimizer = torch.optim.AdamW(model.parameters(), lr=learning_rate)&#10;&#10;for epoch in range(num_epochs):&#10;    &#35; The rank slices differ but come from the same epoch shuffle.&#10;    sampler.set_epoch(epoch)&#10;    for x, y in loader:&#10;        x = x.to(local_rank)&#10;        y = y.to(local_rank)&#10;        optimizer.zero_grad()&#10;        loss = model(x, y)&#10;        loss.backward()       &#35; DDP synchronizes gradients here.&#10;        optimizer.step()&#10;&#10;dist.destroy_process_group()</code></pre>
</div>
<p><code>torchrun</code> starts this program once per GPU and supplies
<code>LOCAL_RANK</code>. <code>DistributedSampler</code> partitions
dataset indices among ranks. DDP registers the gradient synchronization
used by <code>loss.backward()</code>. NanoGPT uses the same
one-process-per-GPU DDP structure <span class="citation">[<a href="#ref-karpathy-nanogpt">4</a>]</span>. Instead of a distributed sampler,
each rank calls <code>get_batch()</code>. A rank-dependent seed gives
the ranks different random streams.</p>
<h2 id="olmo-data-organization-under-ddp">OLMo data organization under
DDP</h2>
<p>DDP synchronizes gradients, but it does not decide which data a rank
receives. OLMo presents training data through an indexed
<code>InstanceSource</code>. An instance index
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6595em;"></span><span class="mord mathnormal">i</span></span></span></span>
is the address of one model input, not a token ID. The meaning of that
address depends on the concrete source. For a
<code>ConcatAndChunkInstanceSource</code> with sequence length
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6833em;"></span><span class="mord mathnormal" style="margin-right:0.0576em;">S</span></span></span></span>,</p>
<p><span class="katex-display"><span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6705em;vertical-align:-0.011em;"></span><span class="mord mathnormal">i</span><span class="mspace" style="margin-right:0.2778em;"></span><span class="mrel">⟼</span><span class="mspace" style="margin-right:0.2778em;"></span></span><span class="base"><span class="strut" style="height:0.7778em;vertical-align:-0.0833em;"></span><span class="mord text"><span class="mord texttt">source[i]</span></span><span class="mspace" style="margin-right:0.2778em;"></span><span class="mrel">=</span><span class="mspace" style="margin-right:0.2778em;"></span></span><span class="base"><span class="strut" style="height:1em;vertical-align:-0.25em;"></span><span class="mord text"><span class="mord">tokens</span></span><span class="mopen">[</span><span class="mord mathnormal">i</span><span class="mord mathnormal" style="margin-right:0.0576em;">S</span><span class="mspace" style="margin-right:0.2778em;"></span><span class="mrel">:</span><span class="mspace" style="margin-right:0.2778em;"></span></span><span class="base"><span class="strut" style="height:1em;vertical-align:-0.25em;"></span><span class="mopen">(</span><span class="mord mathnormal">i</span><span class="mspace" style="margin-right:0.2222em;"></span><span class="mbin">+</span><span class="mspace" style="margin-right:0.2222em;"></span></span><span class="base"><span class="strut" style="height:1em;vertical-align:-0.25em;"></span><span class="mord">1</span><span class="mclose">)</span><span class="mord mathnormal" style="margin-right:0.0576em;">S</span><span class="mclose">]</span><span class="mord">.</span></span></span></span></span></p>
<p>Adjacent indices in this source address adjacent, non-overlapping
token ranges <span class="citation">[<a href="#ref-olmo-concat-and-chunk-source">7</a>]</span>. This is not
guaranteed for every source. A <code>SamplingInstanceSource</code> can
deliberately map multiple indices to the same child instance when it
repeats a dataset <span class="citation">[<a href="#ref-olmo-sampling-instance-source">9</a>]</span>.</p>
<p>A <code>PackingInstanceSource</code> precomputes which documents
belong to each instance. When <code>source[i]</code> is called, it reads
those document token ranges, concatenates them, and pads the result to
length
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6833em;"></span><span class="mord mathnormal" style="margin-right:0.0576em;">S</span></span></span></span>.
The loader sees the same indexed interface even though the sources
construct an instance differently <span class="citation">[<a href="#ref-olmo-instance-source">6</a>, <a href="#ref-olmo-packing-source">8</a>]</span>.</p>

<p>The implementation is the same transformation <span class="citation">[<a href="#ref-olmo-composable-loader">5</a>]</span>:</p>
<pre class="code-block"><code class="language-python">&#35; One row is one global batch.&#10;rows = global_indices.reshape(-1, instances_per_batch)&#10;&#10;&#35; Skip optimizer steps that were already completed.&#10;rows = rows[batches_processed:]&#10;&#10;&#35; Take this DDP rank&&#35;39;s columns from every remaining row.&#10;local_indices = rows[:, dp_rank::dp_world_size].reshape(-1)</code></pre>
<p>NanoGPT does not build this shared array. Each NanoGPT rank samples
random starting positions independently. Rank-specific seeds give
different random streams, but two ranks can select overlapping token
windows. OLMo instead divides each row of one shared schedule among the
ranks. A scheduled index is therefore assigned to only one rank in a
global batch. With direct consecutive chunking, different scheduled
indices also mean disjoint token ranges. A sampling source can still map
different scheduled indices to the same child instance <span class="citation">[<a href="#ref-olmo-sampling-instance-source">9</a>]</span>.</p>

<p>The source determines the contents of an instance. The index rows
determine the global batches. The column slices determine the local DDP
batches.</p>
<h2 id="from-ddp-to-zero-and-fsdp">From DDP to ZeRO and FSDP</h2>
<p>ZeRO begins with DDP and removes one kind of replicated model state

be the number of data-parallel ranks. Let
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6833em;"></span><span class="mord mathnormal" style="margin-right:0.1389em;">P</span></span></span></span>,
<span class="katex"><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6833em;"></span><span class="mord mathnormal">G</span></span></span></span>,

<p>per rank between computations. At this point parameters, gradients,
and optimizer state are all sharded.</p>
<p>Fully Sharded Data Parallel (FSDP) is PyTorch’s implementation of
this stage-3 pattern <span class="citation">[<a href="#ref-zhao2023fsdp">11</a>]</span>. In OLMo, the process mesh and
sharding policy configure PyTorch FSDP, which supplies the parameter
all-gather and gradient reduce-scatter.</p>
<figure>
<img src="/notes/pre-training/fsdp-layer-communication.svg" alt="Parameter shards are gathered for one layer, used for forward and backward computation, and reduce-scattered into gradient shards." />
<figcaption>FSDP gathers one layer for computation and then returns gradient shards to the owning ranks.</figcaption>
</figure>
<p>The available data-parallel modes are <code>ddp</code>,
<code>fsdp</code>, and <code>hsdp</code> <span class="citation">[<a href="#ref-olmo-data-parallel">12</a>]</span>. The <code>fsdp</code> mode is
the fully sharded endpoint; stages 1 and 2 above explain the progression
to it.</p>
<p>The corresponding OLMo control flow is visible in these abridged
excerpts <span class="citation">[<a href="#ref-olmo-transformer-train-module">13</a>]</span>:</p>
<pre class="code-block"><code class="language-python">from torch.distributed.fsdp import FSDPModule&#10;from torch.nn.parallel import DistributedDataParallel as DDP&#10;&#10;&#35; Construct the process mesh and parallelize the model.&#10;self.world_mesh = build_world_mesh(dp=dp_config, ...)&#10;self.model = parallelize_model(&#10;    model,&#10;    world_mesh=self.world_mesh,&#10;    ...,&#10;    dp_config=dp_config,&#10;)&#10;&#10;&#35; The optimizer is built after DDP or FSDP has been applied.&#10;self.optim = optim.build(self.model, strict=True)&#10;&#10;&#35; PyTorch DDP or FSDP performs its communication through autograd.&#10;loss.backward()&#10;self.optim.step()</code></pre>
<p>The model is sharded before the optimizer is constructed. The
optimizer therefore receives local parameter shards and creates its
per-parameter state for those shards. Supported optimizers can be
selected through configuration. A new optimizer requires a configuration
and build implementation. Ordinary per-parameter state works with the
same FSDP algorithm; global cross-parameter state or custom
communication requires additional integration.</p>
<p>The data assignment from Section 3 is unchanged. FSDP changes the
ownership and communication of model state, not the sequence indices
assigned to ranks.</p>
